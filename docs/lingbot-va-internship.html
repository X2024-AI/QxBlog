Why this matters for a research lab

This wasn't "made a model run faster." It was: profile a diffusion policy and prove it's CPU-launch-bound, not GPU-bound; reject the four standard accelerators with measurements instead of guesses; ship a fix whose output is provably bit-identical across 4,680 attention calls; and then make the result observable with a real-time panel. That's the loop a graduate student or research engineer runs every day.

01Context

北京万仞智慧智能科技有限公司 builds an embodied-AI stack around the OpenArm dual-arm robot. LingBot-VA is the lab's video-action policy: it conditions on multi-camera observations and predicts action chunks autoregressively, served over websocket. My work sat where the model meets the real system — making it fast enough to control a robot in real time, and reliable enough to deploy, evaluate, and monitor on a shared 8×A100 cluster.

Inherited: a working but ~79×-too-slow model, an eval harness full of placeholders, and no observability/ops tooling around the server.

02The headline: 2.65× faster, bit-identical

The model ran at 10,278 ms per action chunk against a 130 ms streaming budget. I was asked to try FP8 / TensorRT-LLM / FlashInfer — but profiled first, and the profile changed the whole plan: GPU utilization was 23.4%. The server was launch-bound, not compute-bound.

PhaseBeforeAfterSpeedup
infer (one chunk: 25 video + 50 action steps)10,278 ms3,878 ms2.65×
compute_kv_cache1,127 ms872 ms1.29×

The three fixes: a sync-free ring-buffer KV cache (replacing a slot pool that called torch.nonzero per layer per step — ~6.5 s of CPU stall), skipping FSDP at world_size=1 (~4.3 s/chunk of hidden allgather churn), and hot-path cleanup. The four "obvious" accelerators were all wrong for this workload — FP8 (no sm80 tensor cores), TensorRT-LLM (wrong model class), paged-KV (the ring buffer already solved it), FlashInfer (attention was only 7.5% of GPU time).

03Verification — why "fast" isn't enough

I proved the speedup is numerically lossless, not just faster: outputs are bit-identical to baseline across all 4,680 attention calls of a full control sequence, via digest-stream diffing and a 6-case equivalence suite. That surfaced a subtle bug in my own first implementation (a transient-path key rebind silently zeroing the KV pool — missed by unit tests, caught by the diff) and two latent bugs in the legacy pool. A result you can trust, not just a faster number.

04Making it observable — a real-time monitoring panel

Built a web panel (script/inference_panel.html, probes at 0.0003% overhead) showing per-phase latency, trend vs the 130 ms budget, and a phase-share advisory (optimize / later / skip, with reasons). It immediately caught a real regression: a neighbor job (~200 CPU processes) inflating every phase 3.8 s → 8–9 s — the launch-bound signature, invisible to a bare latency number.

07What I took away

Profile before optimizing. The four "obvious" accelerators were all wrong; the real win was a nonzero call and an accidental FSDP wrap — things only a profile reveals. And on the ops side: a serving process is only as reliable as the process-tree topology you launch it under.
